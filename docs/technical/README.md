# Техническая документация Core / OSS

Этот раздел — точка входа для контрибьюторов и сопровождающих self-hosted-версию «Виджета отзывов». Он описывает систему, а не историю отдельных задач. Для использования продукта начните с [корневого README](../../README.md).

**Срез исходников: 2026-09-17.** Документация учитывает рабочее дерево, в том числе незакоммиченные изменения. Это не утверждение о составе опубликованного релиза или состоянии конкретного сервера.

## Как читать статусы

- **Текущее** — найдено в исходниках этого среза. Само по себе не означает, что сценарий проверен на стенде.
- **Принятое направление** — архитектурное решение, которое ещё может требовать реализации.
- **Открытый вопрос** — поведение не определено; автор PR не должен выбирать его незаметно.
- **Историческое** — описание старого состояния или план работ, не инструкция к текущей версии.

Конкретная проверка подтверждает только выполненный сценарий и конкретный артефакт. Компиляция не доказывает работу UI, платежей или изоляции данных.

## Область публичной документации

Core — полноценное автономное приложение. Ему не нужны закрытый репозиторий, облачная учётная запись или платная активация. Он содержит сбор отзывов, хранение, админку, редактор и виджет.

Публично документируются общие точки расширения, механизмы безопасности и контракты. Закрытая поставка может добавлять регистрацию клиентов, коммерческие правила и дополнительные страницы. Её исходники, эксплуатационные параметры и коммерческие решения не являются зависимостью этих документов.

Разделение исходников не означает независимость контрактов: изменение общего API или формата данных требует проверки его потребителей.

## Что делать со старыми материалами

Исторические рабочие спецификации и планы не входят в публичную документацию. Они могут описывать прежнюю структуру, прототипы и незавершённые задачи. Источники текущего состояния — код и поддерживаемые документы этого раздела, а не отметка «утверждено» в плане.

В частности, материалы self-hosted/cloud от 2026-09-14 описывают более широкую модель нескольких аккаунтов маркетплейса. В текущем срезе credentials остаются уникальными по тенанту и маркетплейсу. Новая техническая документация не объявляет прежний план реализованным.

Поддерживаемый self-hosted-путь — Docker Compose со сборкой образа из checkout. Локальная сборка без Docker документируется только для разработки.

## Правила обновления документации

1. Изменяете контракт, переменную окружения, хранение или процедуру выпуска — обновляйте соответствующий документ в том же PR.
2. Описывайте наблюдаемое поведение, границы и ошибки. Не дублируйте построчно реализацию.
3. Ссылайтесь на файл и имя символа; номера строк быстро устаревают.
4. Отделяйте миграцию от конечного состояния. Не называйте целевую схему существующей.
5. Команды должны иметь рабочий каталог, предпосылки и предупреждение о записи данных.
6. Примеры используют тестовые данные. Пароли, токены, пользовательские отзывы и внутренние адреса в публичные документы не включаются.
7. Проверяйте ссылки и выполняйте затронутый безопасный сценарий. В PR указывайте, что действительно проверено и что не проверялось.

Новый документ нужен, когда появился отдельный вопрос с устойчивым ответом. Для небольшого уточнения дополняйте существующий раздел, а не создавайте ещё один конкурирующий источник.
